# Credential broker: per-participant authority for tool calls

*Research memo, 2 October 2026. Topic: how a tool call in a shared session runs with the authority of the humans who approved it. cursor.com, forum.cursor.com, ietf.org, datatracker.ietf.org, rfc-editor.org, workos.com and developer.hashicorp.com were all egress-blocked; every claim below rests on search snippets and is marked UNVERIFIED where it goes beyond what the snippet states.*

## Why it matters for Henosis

Henosis's whole pitch is "one agent, many humans". The kernel already answers *who may steer* (authority lattice, arbitration) and *who must consent* (risk class, quorum bound to the hash of the exact call). It does not yet answer *whose keys the action uses*. Today the runner holds one `ANTHROPIC_API_KEY` and `shell.run` executes as the server's user; `docs/07_security_and_compliance.md` and `docs/09_threat_model.md` both list "server-side credential broker keyed by the approver" as a phase-1 gap. Without it, every property Henosis proves about approvals stops at the tool boundary: Bo can approve, the hash is bound, the vote is journaled, and the PR still opens under Ana's GitHub token because Ana started the session. The broker is what makes the approval model true end to end, in the desktop and web clients first, then in the fleet ledger and team memory ("Ana's fact is Ana's fact" should extend to "Ana's PR is Ana's PR").

## Prior art

1. **Cursor Team Followups** (cursor.com/docs/cloud-agent/settings.md and forum.cursor.com thread 158866, accessed 2026-10-02, both UNVERIFIED, snippets only). Admins choose Disabled / Service accounts only / All. Cursor's own docs warn that a follow-up "can instruct the agent to read environment variables, print secrets to logs, push credentials to an external endpoint, or perform actions using the original creator's access tokens". The forum post frames the session as a "bearer-token-equivalent capability" shareable by URL or Slack thread membership with "no per-prompt re-authorization of the requester".
2. **RFC 8693 OAuth 2.0 Token Exchange** (rfc-editor.org/rfc/rfc8693, accessed 2026-10-02). Distinguishes impersonation from delegation: a delegated token keeps the user as `sub` and records the acting party in an `act` claim; `act` can nest to record a chain of intermediaries, newest outermost. The IETF draft *OAuth 2.0 Extension: On-Behalf-Of User* (draft-oauth-ai-agents-on-behalf-of-user-02, August 2025, accessed 2026-10-02, UNVERIFIED) applies this to agents with an actor token for the agent identity.
3. **Okta Cross App Access / ID-JAG and MCP Enterprise-Managed Authorization** (workos.com/blog/id-jag-cross-app-access and nirmata.com 2026-08-18, accessed 2026-10-02, UNVERIFIED). An RFC 8693 exchange at the enterprise IdP turns a user identity into a short-lived single-audience identity assertion grant, minted only if an admin approved the app-to-app connection; an RFC 7523 jwt-bearer grant at the resource turns it into a scoped access token. Adopted by the IETF OAuth WG in September 2025 and into MCP in November 2025.
4. **Arcade.dev** (arcade.dev blog and workos.com comparison, accessed 2026-10-02, UNVERIFIED). A tool-execution layer that runs the OAuth flow with the end user, stores and refreshes tokens, and executes the tool "under that specific user's permissions; the agent never holds credentials". Authorization is just-in-time at execution.
5. **HashiCorp Vault control groups** (developer.hashicorp.com/vault/tutorials/policies/control-groups, accessed 2026-10-02, UNVERIFIED). Multi-party authorization for secret access: the response is wrapped, the request waits for N approvals from a named identity group, and only then can the requester unwrap. Closest analogue to Henosis's quorum, applied to the credential.
6. **Attenuating Agent Tokens and Biscuit** (draft-niyikiza-oauth-attenuating-agent-tokens-01, June 2026; draft-asor-wimse-agent-delegation-chain-01, September 2026; danielvaughan.com 2026-04-11; all accessed 2026-10-02, UNVERIFIED). A signed token encodes the tools an agent may invoke and argument constraints; a holder can derive a narrower token offline, bounded by depth and lifetime; any derivation that widens scope fails verification; enforcement points verify with only the root key.
7. **Microsoft Entra Agent ID** (learn.microsoft.com/entra/agent-id/agent-on-behalf-of-oauth-flow, accessed 2026-10-02, UNVERIFIED). Agent identities cannot start interactive `/authorize` flows; they must receive a user token from a client and perform an OBO exchange.

## What to borrow

- **Delegation, not impersonation** (RFC 8693). The minted credential keeps the approving human as subject and names the Henosis session and agent in `act`.
- **Short-lived, single-audience, minted per grant** (XAA, Entra). The broker never hands out the stored refresh token; it mints a token whose audience is one tool provider, whose lifetime is the expected call duration, and whose existence is logged.
- **Tokens never enter the model context** (Arcade). The runner gets an opaque handle; resolution happens inside `ToolImpl.run` on the server and the output is redacted against every minted secret.
- **Wrapped response released by quorum** (Vault control groups). Henosis's approval record already holds the votes; the broker treats a granted `ApprovalRecord` as the unwrap condition.
- **Attenuation to tool plus arguments** (AAT). The approval id is already `hash(call)`; the minted token should carry that hash so the provider-side proxy (or the broker itself) refuses any use for a different call.
- **Admin-level connection consent** (XAA). Which providers a team's agents may touch is an owner or lead decision, separate from per-call approval.

## What is unsolved

- **Composite principals.** Every standard above has one subject and an actor chain. A quorum of two owners approving one `irreversible` call has no token shape; GitHub will attribute the merge to exactly one account. Henosis has to choose a *principal* among the approvers and record the rest as co-approvers in both the log and the provider's own metadata (co-author trailers, PR body).
- **Scope mismatch between approval and effect.** Binding to `hash(call)` is exact for structured tools (`github.merge_pr`) but says little about `shell.run` with a script argument. Argument constraints in the AAT style only help where arguments are structured; shell stays a container-and-no-network problem.
- **Mid-call revocation.** A participant who leaves or is demoted while a long tool call runs: the token is already minted. Short TTL bounds the window; nothing in the prior art revokes in flight.
- **Where long-lived grants live on desktop.** The Tauri shell can keep a user's own refresh tokens in the OS keychain for a single-user local server, but a shared session needs them on the server that executes the tool; the two modes must not be confused.
- **Replay.** Credential material must never enter the log; replay already relies on recorded tool outputs, so this is consistent, but `henosis verify` must prove no secret-shaped string appears in any event.

## Concrete recommendations for Henosis

1. **Protocol: name the credential need on the tool, not the call.** In `packages/protocol/src/index.ts`, extend `ToolSpec` with `credential?: { provider: "github" | "jira" | "slack" | "shell" | string; scopes: string[] }`, and add events `participant.connected` (actor, provider, scopes), `credential.issued` (approvalId, principal, coApprovers, provider, scopes, expiresAt, tokenHash), `credential.used` (callId, tokenHash) and `credential.refused` (callId, reason). No field ever carries a secret.
2. **Server: `packages/server/src/broker.ts`.** A `CredentialBroker` with `connect(userId, provider)` (OAuth authorization-code flow started from the client, callback on the server), `mint(record: ApprovalRecord, spec: ToolSpec): Promise<ExecutionGrant>` and `revoke(tokenHash)`. `mint` runs only when `record.status === "granted"`, picks the principal by policy (the driver if the driver voted, else the highest-ranked approver), performs an RFC 8693 exchange where the provider supports it (GitHub App user-to-server tokens otherwise), sets TTL to `max(60s, spec.expectedDurationMs)` and audience to the provider, and emits `credential.issued`. Long-lived grants are encrypted at rest through `packages/server/src/storage.ts`; nothing crosses the websocket.
3. **Runner: opaque handles only.** In `packages/runner/src/tools.ts`, add `credentials?: CredentialResolver` to `ToolContext`, with `resolve(provider): Promise<string>` valid only for the duration of the call whose approval minted it. `ToolRegistry` wraps every `run` so the returned output is scrubbed of every string the resolver handed out before it becomes a `ToolResult`. `Runner.execute` in `packages/runner/src/runner.ts` calls the broker between `awaitApproval` returning `granted` and the tool running; a refusal becomes a `ToolResult` with `ok: false` and a `credential.refused` event, which the agent reads like a denied claim.
4. **Policy: approval is not enough without a connection.** Keep `packages/kernel/src/approvals.ts` pure, but let the server reject an `approve` vote with a visible reason when the voter has no `participant.connected` for the tool's provider. In the client this is a quiet notice in the conversation column ("Bo approved; connect GitHub to count").
5. **Client: attribution in the collapsed tool line.** In the `@henosis/web` client (and therefore the Tauri desktop shell), the collapsed tool line gains a muted suffix "as Ana · approved by Ana, Bo"; a per-user Connections list lives under the team page, one row per provider with scopes and a disconnect. Desktop-only local mode may store the user's own grants in the keychain via Tauri's stronghold plugin; shared sessions always use the server broker.
6. **Fleet and memory: carry the principal.** `packages/fleet` records the provider connections an owner or lead has allowed per project (the XAA admin step); `packages/memory` attributes any fact produced by a credentialed call to the principal, with co-approvers kept through compaction. Add two tests: in `packages/server`, "a follow-up by Bo never executes under Ana's credential unless Ana voted on that hash"; in `packages/kernel`, "no `credential.*` event contains a string matching a minted token", run by `henosis verify`.
