# Chat-ops integration depth: Slack, Teams, Discord for a desktop-first Henosis

Researcher memo, 2026-10-02. Topic: slack-and-chat-ops-integration.

## Why it matters for Henosis

Henosis's thesis is that the session, not a chat thread, is the shared object. Chat is still where the team already is, and in the last two months the chat vendors have moved onto Henosis's ground: Slack Code (20 Aug 2026) gives agents a dedicated "code channel" with plan, diff and preview tabs; GitHub Copilot now runs shared cloud-agent sessions from `@GitHub` mentions in Teams (21 Aug 2026) and Slack. The question for Henosis is no longer "should we have a Slack bot" (`packages/slack` exists and is tested) but how deep to go: which actions are safe and legible in a chat message, where the message must hand off to the desktop or web app, and how to stay inside three platforms' rate and interactivity limits without a second product growing inside Slack.

The current adapter (`packages/slack/src/adapter.ts`) already maps team/project/management channels, threads per session, Block Kit approval buttons, management-channel contention buttons and `/fold` slash commands, with 1.5 s coalescing per thread. That is the right skeleton. The gaps are hand-off, correctness under platform limits, Teams, and the one surface Slack now offers that threads cannot match.

## Prior art

1. **Slack Code / code channels** (Slack blog, 20 Aug 2026; slack.dev developer post, 26 Aug 2026; help centre). An agent creates a temporary channel from an originating thread; the channel carries conversation, plan, code diff, HTML preview and canvas as "Artifacts"; status shown in the sidebar ("working" / "needs a response"); "quick actions" are links above the composer (create PR, open in your platform); the channel auto-archives (removed after seven days of inactivity) and posts summaries back to the originating message; line comments on diffs can be batched as a review. Partners at launch: Claude Tag, Devin, GitHub Copilot, Vercel; OpenAI "soon". APIs are beta, partner-only, under a new `code.channels:manage` scope within `assistant:write`. Accessed 2026-10-02. https://slack.com/blog/news/slack-code-channels-for-agents, https://slack.dev/slack-code-a-dedicated-place-for-agent-work/, https://slack.com/help/articles/54310833022355-Build-with-AI-as-a-team-using-Slack-Code
2. **Claude Code in Slack and Claude Tag** (Anthropic docs). `@Claude` in a channel creates a cloud session; Slack gets status updates, a completion summary and four buttons: View Session, Create PR, Retry as Code, Change Repo. Explicit "Slack vs web" guidance: Slack when the context is already in a thread or the task is async; web for uploads, real-time interaction, long tasks. Claude Tag runs as the organisation's shared identity with admin-scoped access bundles per channel and a posted task checklist in-thread. Accessed 2026-10-02. https://code.claude.com/docs/en/slack, https://claude.com/docs/claude-tag/overview
3. **GitHub Copilot in Microsoft Teams and Slack** (GitHub changelog, 21 Aug and 25 Sep 2026). `@GitHub` in a channel, thread or DM starts a cloud agent session "everyone can see and help direct"; only participants with write access to the repo can make it change code; work continues "from your terminal, the GitHub Copilot app, or your preferred IDE". Repo admins can require one extra PR approval for the Teams integration identity. The September update is a list of exactly the failure modes a chat adapter hits: stale replies, reconnection after idle, duplicate answers, superseded sessions acting in the old repo. Accessed 2026-10-02. https://github.blog/changelog/2026-08-21-shared-agentic-work-with-github-copilot-in-microsoft-teams/, https://github.blog/changelog/2026-09-25-updates-to-github-copilot-for-slack-and-microsoft-teams/
4. **Microsoft Teams agent platform** (Microsoft 365 dev blog, Build, 2 Jun 2026). Teams SDK GA (Python/JS/C#); "agent sessions" for long-running work, threaded channel conversations, quoted replies as the human-in-the-loop primitive; apps now allowed in shared and private channels. Accessed 2026-10-02. https://devblogs.microsoft.com/microsoft365dev/build-collaborative-agents-where-work-happens/
5. **Slack platform limits** (docs.slack.dev rate-limits and chat.update pages via search snippets; api.slack.com blocked by proxy, so partly UNVERIFIED): roughly one message per second per channel with short bursts, per-method per-workspace tiers, `chat.update` Tier 3 (50+/min); interactions must be acked within 3 s; `response_url` valid 30 min and 5 uses (independently measured by slack.green, 1 Oct 2026). Accessed 2026-10-02. https://docs.slack.dev/apis/web-api/rate-limits, https://slack.green/en/blog/slack-interactivity-payload
6. **Teams bot rate limits** (Microsoft Learn via snippet, UNVERIFIED direct): per-agent per-thread 7 sends/s, 60 per 30 s, 1800 per hour; all agents per thread 14/s; 50 RPS per app per tenant; back off on 429. Message updates go through `updateActivity(activity.id)`; there is no `response_url`. Accessed 2026-10-02. https://learn.microsoft.com/en-us/microsoftteams/platform/bots/how-to/rate-limit, https://github.com/microsoft/slack-plus-teams/blob/main/docs/interactive-responses.md
7. **Discord interactions** (discord.com blocked; conferbot limits mirror, UNVERIFIED): 3 s initial response or defer (type 5/6), 15-minute interaction token, one initial response, 5 action rows x 5 buttons, 50 RPS global with interaction callbacks exempt. Accessed 2026-10-02. https://www.conferbot.com/limits/discord

## What to borrow

- **The hand-off button set.** Every mature integration converges on a small, fixed set: open in app, create PR, change target, plus a summary. Claude Code's four buttons and Copilot's "continue from your terminal or IDE" are the pattern. Henosis's equivalent is "Open in Henosis" (deep link to the desktop app with a web fallback), "Brief", "Take the seat".
- **Status as a sidebar word, not a message.** Slack Code's channel status ("working / needs a response") maps exactly onto Henosis's five status words (`docs/12_brand.md`): running, awaiting approval, blocked, paused, idle.
- **Write access gates mutation.** Copilot lets anyone steer but only repo writers trigger changes; Henosis's observer/contributor/driver/owner ranks should be the same gate on chat replies, derived from `users.json`, never from Slack membership alone.
- **Post back to the origin.** Slack Code's summary-to-originating-message is the right shape for the fleet brief: the project channel stays quiet, the thread holds the detail.
- **Explicit "use chat when / use app when."** Anthropic writes it down. Henosis should too, and encode it: approvals, pauses, short steers and brief requests in chat; forks, merges, path claims, memory curation and anything that needs the log view in the app.

## What is unsolved

- **Quorum in chat.** No vendor shows M-of-N approval of a hash-bound call in a message. Slack buttons are per-click; the message must be `chat.update`d after each vote and the vote must be rejected if the approval id (hash of the call) no longer matches a pending approval. Stale-click handling is the failure mode GitHub's September changelog is fixing.
- **Identity.** Slack Code agents inherit Slack's identity model; Henosis's authority model is its own. The `users` map in `ChannelMap` is a manual bridge; Teams and Discord add two more id spaces. Unmapped users must be observers, with no vote.
- **Rate limits versus fleet size.** One message per second per channel means a 30-session fleet with per-turn updates saturates a project channel; the 1.5 s thread coalescer does not bound channel-level broadcasts of irreversible approvals. Teams' 1800/hour per thread is tighter than it looks for an hour-long session.
- **Partner-only APIs.** Slack Code channel creation is gated to launch partners. Henosis cannot create code channels today; it can only emulate with ordinary channels and threads, and should not design around an API it cannot call.
- **Context leakage.** Claude Code's docs warn that the agent may follow instructions from other messages in the thread. Henosis's rule that team chat never reaches the agent (README) is a differentiator; the adapter must keep thread replies as directives only when prefixed, and never feed free text into the model.

## Concrete recommendations for Henosis

1. **Add a hand-off block to every Slack and Teams message that needs more than a click.** In `packages/slack/src/adapter.ts`, a shared `handoffBlocks(sessionId, kind)` returning "Open in Henosis" (`henosis://session/<id>` with `https://` fallback), "Brief" and, for approvals, "Open the call". Register the `henosis://` scheme in `apps/desktop` (Tauri deep-link plugin) and route it in `apps/web` to the same session view. Mobile gets the same links second.
2. **Make approval votes idempotent and hash-checked.** On `onAction`, resolve the approval by id, verify it is still pending and that the button's `value` equals the call hash; otherwise `chat.update` the message to "superseded" and reply ephemerally. Store the vote event through `@henosis/kernel` and re-render the tally (`2 of 3 owners`) on each update. Test in `packages/slack/test/adapter.test.ts`: late click after quorum, click after cancel, click from an unmapped Slack user.
3. **Ack first, then work; budget `response_url`.** Bolt in socket mode still requires a 3 s ack. Move all kernel writes in `onAction`/`onSlash` after `ack()`, use `response_url` at most once per click and `chat.update` by `ts` thereafter (30 min, 5 uses). Add a token-bucket per channel (1/s, burst 5) in `packages/slack/src/client.ts` in addition to the per-thread coalescer, with 429 `Retry-After` honoured.
4. **Define a transport-neutral `ChatOps` interface and a second adapter for Teams.** Lift `SlackClient` (post, update, onAction, onMessage, onSlash) into `packages/chatops` (or `packages/slack/src/client.ts` generalised) with `Block` rendered per platform: Block Kit for Slack, Adaptive Cards 1.5 with `Action.Execute` and `updateActivity` for Teams, components for Discord. Teams limits (7/s, 1800/h per thread) and the lack of `response_url` are the two switches. Ship Teams before Discord; Discord is for open-source and community fleets only.
5. **Encode the "chat versus app" boundary in `packages/protocol`.** Tag each directive and action kind with `surface: 'chat' | 'app'`. Chat allows: approve/deny, pause/resume/cancel, `[scope] steer`, `/constrain`, `/fold brief|sessions|memory`. App-only: fork, fold, claim/release paths, resolve memory conflict with edits, seat transfer. Chat buttons for app-only actions deep-link instead of acting. Document in `docs/13_fleet_collaboration.md` Slack section.
6. **Mirror Slack Code's status and origin-summary pattern without its API.** Set the session thread's first message to the status word with a dot, update it on state change only (not per turn), and post the fleet brief once per lead-set cadence to the project channel as a summary that links back to the threads. Keep the "team chat never reaches the agent" rule: thread replies become directives only when they match the `[scope]` or slash grammar; everything else is ignored and logged as a `chat.note` event in the session log for the handoff brief's "what people said" section.
