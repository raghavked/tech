# Auto-update and release pipeline for the Fold desktop shell

Research memo, 2026-10-02. Scope: `apps/desktop` (Tauri v2 shell around `apps/web`), the CI in `.github/workflows/ci.yml`, and the security posture in `docs/07_security_and_compliance.md` and `docs/09_threat_model.md`.

## Why it matters for Fold

The desktop shell is thin: the agent, the log and the arbitration live in the server, and the shell wraps the web client. The updater therefore matters in three specific ways.

1. **Protocol drift breaks the approval path.** Approvals are bound to the hash of an exact tool call and irreversible calls need a quorum of distinct humans. A stale shell that cannot parse a new `packages/protocol` event shape silently drops out of the quorum. The updater is how we keep every seat able to approve.
2. **The updater is the most direct attack on approvals.** The one thing that can replace the code rendering an approval prompt is a malicious update. Signing keys, key rotation and the update endpoint belong in the threat model with the same weight as the session token.
3. **Sessions run for days; the shell must not restart under a driver.** A relaunch while someone holds the driver seat or has an approval open is a user-facing incident even though the server state survives. The update policy has to know what the shell is doing.

Today `apps/desktop/src-tauri/tauri.conf.json` has no updater plugin, `bundle.targets: "all"`, no signing configuration, and `ci.yml` does not build the shell at all. Version is `0.1.0`, identifier `studio.fold.desktop`.

## Prior art

1. **Tauri v2 updater plugin** (`@tauri-apps/plugin-updater`, `tauri-plugin-updater`). Docs: https://v2.tauri.app/plugin/updater/ and plugin README https://github.com/tauri-apps/plugins-workspace/tree/v2/plugins/updater (README fetched 2026-10-02; the v2.tauri.app page is egress-blocked here, details below from snippets, UNVERIFIED). Signatures are mandatory and cannot be disabled: a minisign keypair, private key in CI (`TAURI_SIGNING_PRIVATE_KEY`), public key in `tauri.conf.json`. Endpoints are URL templates with `{{target}}`, `{{arch}}`, `{{current_version}}`; a static `latest.json` or a dynamic server that answers 204 for "nothing for you". The changelog states the updater now supports deb, rpm and AppImage on Linux and NSIS and MSI on Windows (https://v2.tauri.app/release/updater/, snippet, 2026-10-02). JS flow is `check()` then `downloadAndInstall()` then `relaunch()` from the process plugin. No staged rollout, no delta, no rollback built in.
2. **tauri-action** (https://github.com/tauri-apps/tauri-action, fetched 2026-10-02). GitHub Action that builds per OS in a matrix (two macOS jobs for `aarch64-apple-darwin` and `x86_64-apple-darwin`, `ubuntu-22.04`, `windows-latest`), creates or updates a GitHub Release (`tagName`, `releaseDraft`, `prerelease`), and with `uploadUpdaterJson` (default true) emits a `latest.json` pointing at the release assets; `updaterJsonPreferNsis` picks NSIS over MSI. Signing and notarization are driven by env: `TAURI_SIGNING_PRIVATE_KEY`, `APPLE_CERTIFICATE`, `APPLE_SIGNING_IDENTITY`, `APPLE_ID` or `APPLE_API_KEY` + `APPLE_API_ISSUER`.
3. **Sparkle 2 (macOS)** phased rollouts and EdDSA. Atlassian's Sourcetree team contributed phased releases (https://www.atlassian.com/blog/sourcetree/open-source-announcement-phased-releases-for-sparkle-based-macos-apps, egress-blocked, UNVERIFIED): an appcast item carries `sparkle:phasedRolloutInterval`, installs are bucketed into seven groups by a stable per-install random value, and one more group is admitted every interval. Sparkle's key guidance (https://sparkle-project.org/documentation/eddsa-migration, snippet, 2026-10-02): rotate a signing key only by first shipping the replacement public key in an update signed by the current key.
4. **electron-builder / electron-updater** (https://www.electron.build/auto-update, egress-blocked, snippets, 2026-10-02). The staged rollout model to copy: `stagingPercentage: N` in `latest.yml`; the client derives a percentage from a persistent per-install GUID and refuses updates whose staging percentage is below it. Channels (`latest`, `beta`, `alpha`) are separate manifests. Blockmap differential downloads. Squirrel.Windows is explicitly unsupported; NSIS is the Windows target.
5. **Velopack** (https://docs.velopack.io/packaging/signing, snippet, 2026-10-02), the maintained successor to Squirrel with delta packages and a documented path for Azure Trusted Signing. Its note that Trusted Signing certificates no longer carry instant SmartScreen reputation and accumulate it normally is the current state of the art on Windows warnings (UNVERIFIED).
6. **Apple notarization** (https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution, snippet, 2026-10-02; Sequoia Gatekeeper change via https://eclecticlight.co/2024/08/10/gatekeeper-and-notarization-in-sequoia/). Requirements: Developer ID Application certificate, hardened runtime, `notarytool` (altool is dead), staple the ticket for offline verification. Since Sequoia the right-click override for unnotarized apps is gone; an unnotarized Fold build is effectively uninstallable by a normal user.
7. **Tauri Windows signing** (https://v2.tauri.app/distribute/sign/windows/, egress-blocked, snippet, 2026-10-02): either `certificateThumbprint` for a local certificate or `bundle.windows.signCommand` for a cloud signer such as Azure Trusted Signing via `relic` or `trusted-signing-cli`, authenticated with `AZURE_CLIENT_ID` / `AZURE_TENANT_ID` / `AZURE_CLIENT_SECRET`.

## What to borrow

- From Tauri: mandatory minisign signatures, the single `latest.json` contract, and NSIS-only on Windows (`updaterJsonPreferNsis`).
- From electron-updater: per-install GUID bucketing against a `stagingPercentage`. Tauri's static manifest has no such field, so the bucketing moves to a tiny dynamic endpoint that returns 204 below the threshold. The client stays stock.
- From Sparkle: staged rollout in fixed groups with an interval, and the key rotation rule (new public key shipped under the old key before the old key is retired). Also `minimumSystemVersion` and `criticalUpdate` as manifest concepts, expressed in our endpoint as `min_client_version` from the server.
- From Velopack and electron-builder: delta updates matter for Electron-class apps, not for a 10 MB Tauri shell; skip them.
- From Apple: notarize and staple in CI on every tagged build, never by hand.

## What is unsolved

- **Rollback.** Tauri's updater only moves forward by semver. Re-publishing an older version as a higher one (`0.3.1` with `0.3.0`'s payload) works but is ugly; `version_comparator` on the plugin builder would allow true downgrades but is undocumented territory (UNVERIFIED).
- **Linux.** AppImage self-updates cleanly; deb and rpm updating needs elevated install and the behaviour across distros is new and thinly documented. Flatpak and Snap are outside the Tauri updater entirely.
- **SmartScreen.** Even a correctly signed NSIS installer from a fresh Trusted Signing certificate shows a warning until reputation accrues. There is no engineering fix; only time and volume.
- **Update while driving.** No updater has a notion of "the user is in a privileged seat". That logic is Fold's to write, and it needs the shell to know session state the web client already has.
- **Key compromise.** Tauri holds one public key in config. A compromised CI secret means every install trusts the attacker until a key-rotation update ships, and that update can only be trusted if signed by the compromised key. Threshold or TUF-style signing does not exist for Tauri; the mitigation is an air-gapped key and a short list of people who can run the release workflow.

## Concrete recommendations for Fold

1. **Add the updater to the shell.** `apps/desktop/src-tauri/Cargo.toml`: `tauri-plugin-updater`, `tauri-plugin-process`. `apps/desktop/src-tauri/src/main.rs`: register both. `tauri.conf.json`: `plugins.updater.pubkey`, `plugins.updater.endpoints: ["https://releases.fold.studio/desktop/{{target}}/{{arch}}/{{current_version}}"]`, `plugins.updater.windows.installMode: "passive"`, `bundle.createUpdaterArtifacts: true`, and replace `bundle.targets: "all"` with `["app", "dmg", "nsis", "appimage"]`. `capabilities/default.json`: `updater:default`, `process:allow-restart`.
2. **One release workflow, draft then promote.** New `.github/workflows/release-desktop.yml` triggered by tags `desktop-v*`, running `tauri-apps/tauri-action` on a matrix of `macos-14` (`aarch64-apple-darwin` and `x86_64-apple-darwin`), `ubuntu-22.04`, `windows-latest`, with `releaseDraft: true` and `updaterJsonPreferNsis: true`. Secrets: `TAURI_SIGNING_PRIVATE_KEY`, `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`, `APPLE_CERTIFICATE`, `APPLE_CERTIFICATE_PASSWORD`, `APPLE_SIGNING_IDENTITY`, `APPLE_API_KEY`, `APPLE_API_ISSUER`, `APPLE_API_KEY_PATH`, `AZURE_CLIENT_ID`, `AZURE_TENANT_ID`, `AZURE_CLIENT_SECRET`. Notarization runs inside `tauri build` via the Apple API key; `signCommand` in `tauri.conf.json` calls `trusted-signing-cli` for Windows.
3. **Staged rollout as a 40-line endpoint, not a client feature.** New `apps/update-server/` (Cloudflare Worker or a route in `packages/server/src/releases.ts`; keep it separate from the session host). It reads `channels/stable.json` `{ version, notes, pub_date, platforms, rollout_percent, min_client_version }`, hashes a stable install id the shell sends as a header (`X-Fold-Install: <uuid>` stored in app data on first launch) into 0..99, and returns the Tauri manifest only when the bucket is below `rollout_percent`, else 204. Promotion is `scripts/release/promote.mjs stable 5|25|100`, editing one JSON file. Channels are files: `stable.json`, `beta.json`.
4. **Let the server say when a shell is too old.** Add `minClientVersion` to the hello message in `packages/protocol` and have `packages/server` send it. `apps/web` renders a single quiet notice in the register of the approval notices ("Fold needs an update before you can approve. Restart to update.") using `--fold-accent` from `design/tokens.css`, no modal. Below the minimum, the shell still observes but the approve action is disabled client-side, and the server refuses the approval event anyway.
5. **Never relaunch under a driver.** In `apps/web` (desktop-only path behind `window.__TAURI__`): check on launch and every six hours; download silently; install and `relaunch()` only when the current actor holds no driver seat and has no pending approval, otherwise show the "Restart to update" line in the sidebar footer and wait. Mark this in `docs/05_kernel_design.md` as a client obligation, not a kernel one.
6. **Write the key policy down.** `docs/07_security_and_compliance.md`: minisign private key generated offline, held in two places (GitHub environment secret with required reviewers on the `release` environment, and an offline backup), rotated by shipping the next public key under the current key one release before cutover. Add "compromised update signing key" to `docs/09_threat_model.md` with the blast radius and the response (revoke the GitHub environment, ship a rotation release from the backup key, announce in the fleet brief).
